# FX capture routes and control flow

## What the current errors mean

The regression harness passes one float `inputs_embeds` tensor through each wrapper. Plain `torch.fx.symbolic_trace` substitutes a `Proxy` for that tensor and executes the Python `forward`. A Python `if` that asks for the truth value of a Proxy cannot be resolved; the default tracer raises `TraceError`. It does not emit a branch node. Python branches depending only on static configuration, `None`, or concrete arguments may be resolved and only the selected path appears in the graph.

The Qwen symbolic failure is a related limitation: a dtype/metadata operation reaches `torch.finfo` with a Proxy attribute instead of a concrete floating dtype. Shape, dtype, optional-input, and cache logic in Transformer forwards commonly relies on metadata and Python checks that ordinary FX Proxy does not model.

GPT-2 and Qwen did capture with `torch.export` in the user's run. Their exported graphs contain hundreds/thousands of functional ATen operations and parameters, not editable `call_module` Linear nodes. Existing mutation actions are designed around module targets, so zero actions from those graphs is expected with the current action API. Export is a useful capture route but does not itself make those graphs mutation-ready.

## Routes and tradeoffs

| Route | Captures Python `if`? | Graph shape | Best fit / limits |
|---|---|---|---|
| `torch.fx.symbolic_trace` | Only if condition is static/concrete. A Proxy-dependent `if` errors. | Usually preserves module calls and decomposes user modules. | Existing ResNet and project models; low setup cost. Weak for HF metadata/cache behavior. |
| `transformers.utils.fx.HFTracer` (`hf_symbolic`) | Uses metadata-aware proxies and may resolve metadata-backed branches while tracing. It specializes these to the supplied dummy metadata; it does not encode arbitrary data-dependent Python branches. | FX GraphModule, often retains module calls. | Hugging Face models. Installed Transformers 4.45.1 includes `HFTracer` and `transformers.utils.fx.symbolic_trace`; the current GPT-2 `hf_symbolic_editable` route is verified with Torch 2.11. Other model wrappers and package-version pairs still require per-family verification. The convenience HF `symbolic_trace` checks an architecture allowlist; the adapter uses `HFTracer` directly with explicit dummy inputs. |
| `torch.export` | Captures broader Python bytecode. Shape conditions can be guarded/specialized. Real tensor-data branches must use structured operators such as `torch.cond`; export does not turn arbitrary Python `if` into a branch automatically. | Functional ATen graph; module hierarchy is commonly flattened. Explicit higher-order conditional nodes contain branch subgraphs. | Broad capture and tensor metadata. Best current fallback for GPT-2/Qwen; candidate action generators need a functional-node adapter. |
| `torch.jit.trace` | No: records only the path executed by sample values. | TorchScript graph with module identity mostly lowered. | Deployment compatibility, not safe control-flow discovery. |
| `torch.jit.script` | Can compile supported scripted Python control flow. | TorchScript IR, not FX; model and helper code must be scriptable. | Narrow option for scriptable modules. HF models with dynamic Python/cache types often need substantial adaptation. |
| `torch.compile` / Dynamo | Captures Python bytecode and may graph-break or specialize. | Compiler graphs, not a stable general-purpose block-discovery API. | Diagnostics or compiler execution; less suitable as the foundation for durable FX mutation candidates. |
| ONNX / Hugging Face exporters | Exporter dependent. They can lower supported control flow but may specialize or reject unsupported patterns. | ONNX or backend-oriented/export FX graphs. | Deployment. Not a preferred source for module-preserving mutation candidates. |

PyTorch documents `torch.cond` as a prototype structured conditional that carries a predicate plus true/false subgraphs. It requires both branches to have matching signatures and supported tensor inputs/outputs. A model's ordinary `if tensor_condition:` must be rewritten by its author/adapter into `torch.cond`; a general tracer cannot soundly infer both branches from one sample. See [torch.export control-flow guidance](https://docs.pytorch.org/docs/stable/export.html) and [torch.cond](https://docs.pytorch.org/docs/main/cond.html).

Hugging Face exposes `HFTracer`/`transformers.utils.fx.symbolic_trace` for model-aware FX tracing. Its `HFProxy` carries metadata and the tracer patches a set of tensor constructors and methods, including `torch.finfo`. The installed package source confirms that direct `HFTracer.trace` accepts explicit `dummy_inputs` even when the root is not a `PreTrainedModel`. This is why the regression harness now has an `hf_symbolic` route. See the [Transformers FX utilities example](https://huggingface.co/docs/optimum/en/torch_fx/package_reference/optimization).

The Transformers exporters provide version-specific patches around `torch.export` for known model patterns. They are useful for producing deployable artifacts and fixing known export incompatibilities, but their output/backend support and version pinning make them a capture adapter rather than a universal graph-analysis IR. See [Hugging Face exporter extension points](https://huggingface.co/docs/transformers/main/exporters_extend).

## Conditional semantics for region analysis

Capture adapters must label how branches were handled:

1. **Static specialization:** record the chosen branch and the concrete configuration/metadata assumptions. The graph describes only that specialization.
2. **Explicit structured branch:** traverse both `torch.cond` subgraphs and preserve the predicate, operands, and branch outputs. A region crossing the conditional must account for both paths and their matched interfaces.
3. **Unsupported Python control flow:** keep the capture failure and source traceback. Do not claim the captured graph represents the full model.

For region discovery, a higher-order conditional is a node whose branch GraphModules are nested graphs, not ordinary successors in the parent FX graph. `GraphRegionAnalyzer.discover_nested` now analyzes the root and nested GraphModules separately and records each candidate's `graph_path`; `TracedModel.nested_regions()` exposes the same inventory. Branch nodes are deliberately excluded from root `action_sites`: current editors cannot safely rewrite a branch graph through the parent control-flow node. Branch-interface equivalence, cross-branch action planning, side effects, and aliasing still need explicit analysis before branch-local mutation can be offered.

## Recommended route policy

- Existing in-repository models and ResNets: retain `symbolic_trace` as the compatibility default; optionally compare with export.
- Standard Hugging Face Transformers: try `hf_symbolic` first when preserving module nodes matters; record the model class, Transformers/Torch versions, dummy inputs, and specialized optional arguments. Fall back to export for capture coverage.
- New or custom architectures (including LFM3): try their supported model loader and exporter after installing a compatible Transformers version. The installed Transformers 4.45.1 lacks LFM3's `PreTrainedConfig` and `auto_docstring` APIs, and its config class is not a strict dataclass. A temporary Transformers 5.12.1 overlay still lacked model-source APIs (`use_kernel_func_from_hub_with_fallback`, `force_accelerate_hooks`, and `create_recurrent_attention_mask`) and the model called attention-mask helpers with an unsupported `layer_idx` argument. For structural exploration only, process-local shims selected the model's PyTorch convolution fallback and adapted no-cache mask calls. With those shims, the custom LFM3 source instantiated on meta tensors and `torch.export` produced a 2,570-node graph with nested attention subgraphs. The shared analyzers found 154 functional Linear projections; generic generators proposed 1,706 sequential-linear, 288 residual-linear, and 24 gated-MLP width-growth actions at ratio 1.1. One width-growth action executed on a copied meta graph and returned a logits interface of shape `(1, 4, 128000)`. No checkpoint weights were downloaded, and no numerical output or model fidelity was verified. This is structural coverage only; do not treat the temporary shims as a supported loading route.
- Multimedia and time-series models: make adapters per task signature (pixel/audio/video/series inputs, masks, cache state); do not force them into a one-tensor wrapper if it hides actual forward inputs.
- For mutation actions on exported graphs: first build an FX-node action/interface layer over functional operations, or a semantics-preserving reconstruction pass where a functional linear can safely become a module. Do not count the current module-based actions as applicable to a flattened graph.

The earlier exploratory harness compared `symbolic`, `hf_symbolic`, and `export` on GPT-2 and Qwen. GPT-2's HF route produced 970 nodes, 51 module calls, and 25 existing action proposals when traced through `inputs_embeds`; the plain symbolic route failed, while export flattened the graph and produced no module-based actions. The focused GPT-2 fidelity regression uses tokenized prompt IDs, runs the `hf_symbolic_editable` trace through `TracedModel`, propagates the actual integer example for shape-aware action generation, compares logits and greedy generation to the original model, benchmarks both paths, writes full and simplified FX images through the project's graph drawers, and reports proposal counts by generator variant and action class. The editable route identifies all Hugging Face `Conv1D` projections by type rather than module-name suffix and preserves rank-3 tensors without fixed-width reshape nodes. Its latest run captured 591 nodes, 99 module calls, and 49 rank-3 Linear calls; greedy token IDs matched. It generated 12 MLP neuron-growth actions each at ratios 1.1 and 1.5; representative edge, merge, dropout, and neuron-growth actions executed successfully on copies. The current environment still has not loaded LFM3; its custom code failed against the reported Transformers installation (`PreTrainedConfig` was unavailable).
